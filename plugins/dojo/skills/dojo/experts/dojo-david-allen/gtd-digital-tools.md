## When to Use

Use when someone is trying to choose or configure a GTD tool, when tool proliferation is creating friction rather than reducing it, or when someone mistakes a feature-rich app for a functioning GTD system.

## Fails When

- Tool selection becomes a substitute for GTD practice
- Features are enabled that undermine GTD principles (e.g. automatic priority scoring)
- Tools are switched frequently, losing continuity

## Core Concept

Allen is explicit that GTD is tool-agnostic. The system is defined by behaviours and disciplines — capture, clarify, organise, reflect, engage — not by any specific software. A well-maintained index card system outperforms a neglected productivity app in every scenario. The tool matters far less than the practice.

**The minimal requirements for a GTD tool.** Any digital GTD implementation must support: a capture inbox, a projects list, context-based next-actions lists, a waiting-for list, a someday/maybe list, a calendar, and a reference system. That is it. Any tool that supports these data structures — plainly, without overhead — is adequate.

**The current landscape.** As of the mid-2020s, the most commonly used GTD-compatible tools fall into several categories:

- **Dedicated GTD apps:** Things 3 (macOS/iOS), OmniFocus (macOS/iOS), Nirvana. These ship with GTD structures built in: inbox, projects, contexts, waiting-for. They reward GTD practitioners who want purpose-built environments.
- **Flexible task managers:** Todoist, TickTick, Notion, Obsidian. Require configuration to support GTD structures but are highly adaptable and cross-platform.
- **Plain text / simple lists:** Plain text files, Apple Notes, simple note apps. Fast, low-friction, and surprisingly effective for practitioners who resist complexity.
- **Physical + digital hybrid:** Paper inbox tray for physical items, digital app for actions and projects. Many experienced GTD practitioners maintain hybrid systems indefinitely.

**Configuration principles for digital tools:**
1. Create a distinct inbox or capture bucket — the first place everything goes.
2. Create a projects list — ideally a flat list of project names, not a nested hierarchy.
3. Create next-actions lists by context: @computer, @calls, @errands, @waiting-for, @deep-work, @anywhere.
4. Create a someday/maybe list.
5. Use the calendar only for hard commitments (specific day/time) and date-specific information. Do not use the calendar as a task list.
6. Keep reference separate from action. Reference is searchable; action lists are reviewed and executed.

**The tool-switching trap.** Many GTD practitioners spend years in an app evaluation loop, trying each new productivity tool in search of the perfect system. The time spent evaluating, configuring, and migrating produces no output. The goal is a system that is trusted and used, not a system that is optimal on paper.

## How to Apply

1. **Choose the simplest tool that meets the requirements.** If you are new to GTD, start with the simplest tool you will actually use — even plain text lists. Complexity can be added later.

2. **Configure before loading data.** Set up your inbox, projects list, context lists, waiting-for list, and someday/maybe list before you start adding items. The structure enables the system.

3. **Commit to one tool for at least 90 days.** Give any tool long enough to evaluate it under real conditions. Switching during the first month tells you nothing.

4. **Use the calendar for time-specific commitments only.** Resist the temptation to schedule every task. Calendar items are for things that must happen on a specific day at a specific time. Next actions go on context lists.

5. **Maintain the system, not the app.** The weekly review is the practice that keeps GTD alive. A 30-minute weekly review in a simple notes app produces better results than no weekly review in OmniFocus.

## Examples

**Example 1: The over-featured implementation**
A professional built an elaborate OmniFocus system with nested project folders, custom perspectives, review intervals, and defer dates on every task. He spent 30 minutes configuring tasks for every 5 minutes of work. Simplification: he collapsed projects to a flat list, removed defer dates from 90% of items, and reduced his custom perspectives to three. His OmniFocus time dropped and his output rose.

**Example 2: The plain text success**
A senior consultant used three plain text files: INBOX.txt, PROJECTS.txt, and NEXT-ACTIONS.txt (with context headers). No app, no features, no notifications. Weekly review meant reading all three files and updating them. She maintained this system for years with higher reliability than any app she had tried.

## Anti-Patterns

**Tool as system.** Believing that installing a GTD app creates a GTD system. Tools are containers; the system is the discipline of capture, clarification, organisation, reflection, and engagement. A tool that is not filled, processed, and reviewed is an empty shell.

**Feature overload.** Enabling every feature a task manager offers — tags, priorities, due dates, subtasks, reminders — without checking whether each feature serves a GTD function. Most features are noise. The minimum effective set is: inbox, projects, context lists, waiting-for, someday/maybe.

**Perpetual tool evaluation.** Spending significant time comparing and switching between tools. Any decent tool, consistently used with GTD discipline, produces better results than the perfect tool used inconsistently.
